# 0002. Use importlib.metadata for version resolution

- **Status:** Accepted
- **Date:** 2026-11-06
- **Deciders:** Thapelo Magqazana
- **Consulted:** —
- **Informed:** Forge CLI contributors

## Context

Forge CLI must report its own version. The version is read in four places:

1. **`forge --version`** — the user-facing command, used to triage bug reports.
2. **`forge doctor`** — the diagnostics command (planned), which will compare
   the installed version against a blueprint's `min_forge_version`.
3. **`forge.__version__`** — the library API, used by external tools that
   introspect Forge without importing the CLI.
4. **CI scripts** — which check that the installed package matches the tag
   that triggered the build.

All four consumers need the **same answer**: the version of the Forge package
that is actually installed and running. If any two disagree, bug reports are
useless, and CI is meaningless.

Before this decision, the version was a hard-coded string in
`src/forge/cli/main.py`. That was a slow-motion bug:

- **Drift.** Someone bumps `pyproject.toml` but forgets `main.py`.
  `forge --version` now lies, and a bug reporter sends the wrong version.
- **Frozen binaries.** A PyInstaller build strips `importlib.metadata`, so a
  hard-coded string is the *only* way to report a version — but a hard-coded
  string is also the *wrong* way, because it is duplicated from the tag.
- **Untestable.** A test that asserts `forge --version` returns `"0.1.0a0"`
  fails the moment the version bumps. It must assert against the *actual*
  installed version, not a literal.

The constraints on the resolver are:

1. **Correct** — it must report the installed version, not a guess.
2. **Resilient** — it must work from a source checkout (not installed), from
   an installed wheel, and from a frozen binary.
3. **Fast** — it is called on every command that prints the version, which
   may be many times per invocation (e.g., every error message).
4. **Testable** — the fallback path must be exercisable without reinstalling
   the package.
5. **PEP 440 valid** — downstream parsers use
   `packaging.version.Version`, which rejects `"unknown"`.

The question, then, is not *whether* to resolve the version dynamically. The
question is *how*.

## Decision

We will resolve the Forge version from **`importlib.metadata`**, with a
documented chain of fallbacks, implemented in
`forge.core.version.get_version()`.

### Resolution order

The resolver tries four sources, in order, and returns the first one that
succeeds:

1. **`importlib.metadata.version("forge-cli")`** — the normal path. Reads
   from the installed package's `dist-info/METADATA`. This is the same
   source `pip show forge-cli` reads, so the two cannot disagree.

2. **`forge._version.__version__`** — the bundled fallback, generated by
   `hatch-vcs` at build time. Present in installed wheels and in frozen
   binaries (PyInstaller, Nuitka, cx_Freeze). Absent in a bare source
   checkout.

3. **`FORGE_VERSION` environment variable** — a testing and CI escape hatch.
   Only consulted when the first two sources fail, so it can never mask a
   real installed version. This is intentional: a CI job that sets
   `FORGE_VERSION` must not accidentally override the real installed
   version, because that would make tests pass against a version that does
   not match the code under test.

4. **`"0.0.0.dev0"`** — the honest fallback. Chosen over `"unknown"`
   because `"0.0.0.dev0"` is a valid PEP 440 version, so downstream
   parsers do not crash. It is also clearly a development placeholder, so
   users do not mistake it for a real release.

### Caching

The result is cached with `@lru_cache(maxsize=1)`. This is not a
performance optimisation — it is a correctness invariant. A CLI that
reports different versions on the same invocation is a bug. Caching the
result makes the version immutable for the lifetime of the process.

### Library-facing export

`forge.__version__` is set at import time from `get_version()`. This is the
standard Python convention (`sys.version`, `platform.python_version()`,
every major library). Callers who need a fresh read can call
`forge.get_version()` after `get_version.cache_clear()` — though in
practice, the cache never needs clearing outside of tests.

### What is *not* resolved

The resolver does **not** read `pyproject.toml` at runtime. `pyproject.toml`
is not shipped in the wheel; an installed Forge does not have one to read.
The version that `hatch-vcs` writes into `_version.py` at build time *is*
the version from `pyproject.toml` (plus the Git tag metadata), so reading
`pyproject.toml` at runtime would be both redundant and wrong.

## Consequences

### Positive

- **No drift.** `forge --version` and `pip show forge-cli` read from the
  same metadata. They cannot disagree.

- **Works everywhere.** The four-step chain covers installed wheels,
  editable installs, source checkouts, frozen binaries, and CI test
  harnesses. A contributor who clones the repo and runs
  `uv run forge --version` gets the correct version, even without an
  editable install.

- **Testable without reinstall.** The fallback chain is exercised by
  patching `forge.core.version.version` to raise `PackageNotFoundError`,
  and by patching `sys.modules` to simulate the presence or absence of
  `forge._version`. No subprocess, no reinstall, no `pip uninstall`.

- **PEP 440 valid.** Downstream version comparisons (e.g.,
  `Version(get_version()) >= Version(blueprint.min_forge_version)`) work
  correctly even in the fallback case. A blueprint requiring
  `forge >= 0.1.0` will correctly reject the fallback, so a development
  checkout cannot silently masquerade as a supported release.

- **Fast.** `@lru_cache(maxsize=1)` means the metadata is read once, not
  on every call. A CLI that logs the version on every command does not
  pay ~5ms per log line.

- **Library-friendly.** `forge.__version__` is available without
  importing the CLI, so external tools (test harnesses, dashboards, CI
  scripts) can read the version without pulling in Typer and Rich.

### Negative

- **One more module.** `forge.core.version` is a new module with its own
  tests. This is a small cost for a large correctness win.

- **`_version.py` is generated.** It is listed in `.gitignore` and never
  committed. Contributors who run `git status` and see it must know not
  to commit it. This is documented in the module docstring and in
  `.gitignore` itself.

- **`@lru_cache` requires an explicit `cache_clear()` in tests.** A test
  that simulates a version change must clear the cache first. This is
  documented in the test file's `autouse` fixture, but it is a
  non-obvious detail for new contributors.

- **The `FORGE_VERSION` override is a footgun in disguise.** It exists
  for CI, but a developer who sets it in their shell profile and forgets
  about it will see a version that does not match reality. The
  precedence (metadata wins over env var) mitigates this, but only when
  the package is installed. In a bare source checkout, the env var
  override *will* take effect. This is documented, but it is still a
  risk worth noting.

- **Frozen binaries require an extra build step.** `hatch-vcs` writes
  `_version.py` during `uv build`, but a PyInstaller invocation must
  include that file in the bundle. This is a configuration detail that
  will need to be verified when the first frozen binary is produced.

## Alternatives Considered

### Alternative 1: Hard-code the version in `main.py`

**Why rejected:** This is the status quo, and it is the bug. The version
drifts from `pyproject.toml` the moment someone bumps one without the
other. It cannot be tested without a literal assertion that fails on
every bump. It cannot be correct in a frozen binary, because the
hard-coded string is duplicated from the tag.

### Alternative 2: Read `pyproject.toml` at runtime

**Why rejected:** `pyproject.toml` is not shipped in the wheel. An
installed Forge does not have a `pyproject.toml` to read. It would work
in a source checkout and fail in an installed package — the exact
opposite of what we need.

### Alternative 3: Run `git describe --tags` at runtime

**Why rejected:** Requires a `.git` directory, which is absent from
installed packages and from frozen binaries. It is also slow (~50ms per
call) and fragile (tag formats vary). It fails in shallow clones and in
CI environments that do not fetch tags.

### Alternative 4: Use `setuptools_scm` directly

**Why rejected:** `setuptools_scm` writes `_version.py` at build time,
which we already do via `hatch-vcs`. But `setuptools_scm`'s *runtime*
API also tries to read `.git`, so it has the same problem as
Alternative 3. The build-time generation is useful; the runtime lookup
is not.

### Alternative 5: Return `"unknown"` as the fallback

**Why rejected:** `"unknown"` is not a valid PEP 440 version.
Downstream code that does `Version(get_version())` would crash. It also
loses the signal that the fallback is a *development* environment —
`"0.0.0.dev0"` says "I am a dev checkout", `"unknown"` says "I have no
idea what I am", which is less useful.

### Alternative 6: Ship a static `_version.py` and edit it on every release

**Why rejected:** Requires a release checklist step that is easy to
forget, and produces the same drift problem as Alternative 1, just
moved from `main.py` to `_version.py`. `hatch-vcs` solves this by
generating the file automatically from the Git tag, so there is no
manual step and no drift.
